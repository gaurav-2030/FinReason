Problem statement

Problem statement

Build a router that, for every query, chooses the cheapest retrieval pipeline that still answers correctly — minimising tokens, latency and cost per query at a fixed accuracy target.

Input

An open-domain question; a Wikipedia passage index; three pipelines of rising cost

Output

The answer, the pipeline used, and its tokens, latency and $ / GPU-seconds

Target

Accuracy within ~1 point of always using the best pipeline, at much lower cost

RAG treated as a cost-versus-accuracy optimisation, not a single fixed pipeline.
RAG Router · Review 1PES University · UE24AM343AB53
Objectives

Objectives

  1. Build three pipelines of increasing cost over one Wikipedia index: no retrieval, dense, hybrid + reranking
  2. Compare up-front routing (classify the query first) with a confidence-based cascade (try cheap first, escalate)
  3. Measure cost with one realistic model — tokens, embeddings, reranker and search time, index size — in $ and GPU-seconds
  4. Test whether a tiny router works as well as an LLM router, and whether routers transfer to new domains

Research gaps

Gaps we address

Up-front vs cascade

Routing before answering and escalating after a cheap attempt are rarely compared under one cost model.

Unrealistic cost

Papers count LLM calls or retrieval steps; reranker latency, embedding calls and index size are left out.

Router overhead

If the router is itself an LLM, does it cost more than it saves?

Transfer

Routers are trained and tested on the same datasets; behaviour on new domains is unknown.

Approach 2/5

Two ways to route: up-front vs cascade

Up-front router

  1. Classify the query text → P0, P1 or P2
  2. Run only that pipeline
  3. Return the answer
  • + one pass, predictable latency
  • − decides blind, before seeing any evidence

Cascade with escalation

  1. Run P0 → confidence c₀
  2. If c₀ < τ₀ → run P1 → c₁
  3. If c₁ < τ₁ → run P2
  • + uses real evidence of difficulty
  • − hard queries pay for every stage

Confidence signals: answer log-probability · self-consistency (agreement of 3 samples) · retrieval score gap (top-1 − top-2).

Sweeping the thresholds τ traces a Pareto curve; we compare both designs at equal accuracy.

Approach 4/5

A realistic cost model

Cost per query
Cost(q) = p_in·T_in + p_out·T_out # LLM tokens + p_emb·N_emb # embedding calls + p_gpu·(t_rerank + t_router) # GPU-seconds + p_cpu·t_search # BM25 / FAISS search + index memory cost / queries served # amortised index

Measured

Tokens from the LLM API; wall-clock timings for every stage

Priced

Public API prices per token; cloud GPU price per second

Reported

$ per 1,000 queries and GPU-seconds per query, next to accuracy

One number per query that includes retrieval, reranking and the router — not just LLM calls.

Approach 5/5

Experimental design

Policies compared

  • Always P0 / P1 / P2
  • Random routing
  • Up-front router × 4 sizes
  • Cascade × 3 confidence signals
  • Oracle (cheapest correct) — upper bound

Metrics

  • Exact match and F1
  • Tokens per query
  • Latency p50 / p95
  • $ per 1k queries, GPU-s per query
  • Router accuracy vs oracle labels

Analysis

  • Accuracy–cost Pareto curves vs always-P2
  • Cost saved at ≤ 1 pt accuracy drop
  • Bootstrap 95% CIs, McNemar tests
  • Out-of-domain: train HotpotQA → test NQ, 2Wiki, university docs
The headline result is a Pareto curve: same accuracy as the best pipeline, at a fraction of the cost.

Novelty

What is new

  • Up-front vs cascade, head-to-head under one cost model, with three confidence signals.
  • A realistic cost model in $ and GPU-seconds that includes reranker, embeddings, search and index — not just LLM calls.
  • Router-size study: does a 1 ms classifier route nearly as well as an LLM, once each pays its own cost?
  • Out-of-domain transfer: train on HotpotQA, test on NQ, 2Wiki and our university documents.
  • Honest positioning: outcome-based labels follow Adaptive-RAG [10]; our contribution is cost, cascades and transfer.
