Slide 2 · Six layers (~55 s)

Our system is built in six layers, like floors of a building. Let me go from the bottom up. The data layer loads our three datasets and puts every question into the same format. The context layer turns each table into text that the model can read, and can pick out the most useful rows. The reasoning layer is the heart of the system. It has the prompts, the strategies, the connection to the model, the safe sandbox for running code, and our grounding checker. The optimization layer runs the automatic prompt tools, DSPy and TextGrad. The evaluation layer checks every answer, finds the type of mistake and does the statistics. And the top layer saves every answer and shows the results in charts and in our web app.

Slide 3 · How one question flows (~60 s)

Now let me follow one question through the system, step by step. Take the Titan revenue question. First, we load the question with its table and text. Second, we turn the table into text, for example as a Markdown table. Third, we build the prompt for the chosen strategy, for example 'write Python code'. Fourth, the model answers. We use Qwen3, which runs on our own laptop through a program called Ollama. Fifth, if the model wrote code, we run it in a safe sandbox. If not, we read the line that starts with 'Answer'. Sixth, we check if the answer is correct. Seventh, if it is wrong, we find out why. Eighth, we save everything as one line in a file. The experiments and the web app both use exactly these steps.

Slide 4 · Key modules (~55 s)

The code is split into modules. Each module has one job. data.py loads the three datasets. tables.py turns tables into text, and retrieval.py finds the most useful rows. prompts.py and strategies.py contain all the prompts and strategies. Every strategy works the same way from the outside, so it is easy to add a new one. llm.py talks to the model. It also saves every answer in a cache, so if an experiment stops, we can restart it without losing work. sandbox.py runs the model's code safely, and verify.py checks the numbers in the code. Finally, answers.py, errors.py and metrics.py check the answers, sort the mistakes into types, and calculate the statistics. I now hand over to Sunay, who will present the next part, starting with “Strategies compared”.

Sunay R Hegde

Slide 5 · Strategies compared (~50 s)

Thank you, Gaurav. These are the strategies we compare. Let me explain each one simply. Direct: we ask for the answer only, with no working. Chain-of-Thought: we ask the model to think step by step — with no examples, or with three worked examples. Decomposition: the model first writes the formula, then lists the numbers, then does one step at a time. Program-of-Thought: the model writes Python code and the computer calculates. Self-Consistency: we ask five times and take a vote. VPSC is our own method, and DSPy and TextGrad are the automatically improved prompts. To keep it fair, all strategies use the same instructions, the same answer format and the same worked examples. Only the strategy changes.

Slide 6 · Three datasets (~45 s)

We use three datasets. FinQA comes from American company earnings reports. We use 100 test questions, picked at random but fixed, so every strategy gets the same questions. TAT-QA comes from annual reports. We use 100 questions that need calculation. And our own Indian set has 44 questions. Look at the charts. The left chart shows how many calculation steps each question needs. Most FinQA questions need one step. TAT-QA and the Indian set have many more questions with three or more steps, so they are harder. The right chart shows where the numbers are: mostly in the table, but sometimes in the text, or in both.

Slide 7 · How we built and checked it (~60 s)

This slide shows how we built the Indian set, step by step. We downloaded the official annual reports of Titan, Asian Paints, Marico and Pidilite. We found the profit and loss statement and the balance sheet, and we copied the rows exactly as printed. For every question, we wrote a formula. The correct answer is calculated by running the formula. We never typed an answer by hand, so there are no typing mistakes. We also added automatic checks. All 366 numbers we copied must appear on the original PDF page, or the program stops with an error. And for this review, we checked all 44 questions again against the PDF pages ourselves. All 44 passed. I now hand over to Hanshal, who will present the next part, starting with “VPSC: Verified Program Self-Consistency”.

Hanshal Nagesh

Slide 8 · VPSC: Verified Program Self-Consistency (~60 s)

Thank you, Sunay. This is our own method, VPSC, which stands for Verified Program Self-Consistency. Let me explain it with the picture. We give the model the question and ask it to write a Python program — not once, but five times. The first program is the model's best guess. The other four are a little more varied. We run all five programs in the sandbox. Then comes our new step: the grounding check. We look at every number inside each program. If a program uses a number that is not in the report, it is probably made up, so we throw that program away. Then the programs that are left vote, and the most common answer wins. To test if the check really helps, we also run the same five programs without the check. Then we compare.

Slide 9 · DSPy and TextGrad design (~55 s)

These are the two automatic prompt tools. On the left is DSPy. We give it 50 training questions. It runs the model on them and keeps the examples the model solved correctly. Those examples are then put into the prompt. The MIPROv2 version also tries different instructions and keeps the best combination. On the right is TextGrad. Here, the instruction text itself is improved. The model answers a few questions. When an answer is wrong, a bigger model acts like a teacher: it explains the mistake and rewrites the instruction. We keep the new instruction only if it does better on a separate set of practice questions. Very important: both tools only use training questions. They never see our test questions, so the test stays fair.

Slide 10 · Scoring rule (~60 s)

This is how we decide if an answer is correct. An answer is correct if it is within half a percent of the true answer. So small rounding differences are fine. For percentages, we accept both forms. For example, 12.5 and 0.125 are both correct for 12.5 percent, because one dataset writes percentages as fractions. Our answer reader understands the rupee and dollar signs, Indian grouping like 1,00,000, brackets for negative numbers, and words like crore and lakh. To compare two strategies fairly, we use a statistical test called McNemar's test. It looks only at the questions where one strategy was right and the other was wrong. We use the same scoring everywhere, so all results can be compared. I now hand over to Dhruvagouda, who will present the next part, starting with “Sandbox: running model code safely”.

Dhruvagouda

Slide 11 · Sandbox: running model code safely (~55 s)

Thank you, Hanshal. When the model writes code, we cannot trust it. The code could try to read our files or run forever. So we run it in a sandbox, which is a safe, closed box. It has four layers of protection. First, before running, we check the code. Only the math library is allowed. Anything touching files, the internet or the system is blocked. Second, every program runs in its own separate Python process, away from our main program. Third, only safe built-in functions are available. Fourth, there is a time limit of five seconds. If the code takes longer, we stop it. If the code has an error, we show the error to the model once, and it gets one chance to fix it.

Slide 13 · First results (Qwen3-1.7B, accuracy %) (~55 s)

Here are our first results, with the small 1.7 billion parameter model. The numbers are the percentage of questions answered correctly. Look at the first row. When we ask for the answer directly, with no working, the model gets at most 11 percent. It is almost always wrong. Now look at the other rows. As soon as we ask the model to show its reasoning, accuracy jumps to between 44 percent and 77 percent. Program-of-Thought, where the model writes code, is the best on FinQA with 57 percent, and on our Indian set with 77 percent. On TAT-QA, step-by-step reasoning with examples is best, with 73 percent. So even a small model becomes useful when we prompt it well. We will show the full analysis in Review 3.
