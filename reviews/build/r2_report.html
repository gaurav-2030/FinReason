1. Overview

FinReason answers numerical questions over financial report pages with Large Language Models and measures how prompting strategies and automated prompt optimization change accuracy, cost and reliability. This document presents the high-level design of the system and the data-collection work: the public benchmarks FinQA [1] and TAT-QA [2], and a new test set of 44 questions built from four Indian annual reports.

2. Design goals and constraints

  • Controlled comparison: every strategy must see the same questions, context, scorer and model; only the prompt may differ.
  • Reproducibility: fixed seeds, pinned library versions, deterministic decoding (temperature 0 except for sampling strategies), cached responses.
  • Auditability: every answer must be traceable to its prompt, raw output, generated code, variable trace and evidence rows.
  • Safety: model-generated code is untrusted and must run isolated.
  • Runs on a laptop: local models (Ollama, 4-bit Qwen3 [29]) on an Apple M4 with 24 GB; long experiment queues must be resumable.
  • Provider-agnostic: the same code must run API models (OpenAI-compatible providers, Anthropic) for future comparison.
  • No test leakage: few-shot examples and all optimization data come from FinQA train/dev only.

3. System architecture

The system is organized in six layers (Fig. 1). The data layer loads the three datasets into one common Example structure. The context layer serializes tables and optionally retrieves the most relevant rows and sentences. The reasoning layer holds the prompt library, the strategy engine, the LLM client, the code sandbox and the grounding verifier. The optimization layer compiles DSPy programs and TextGrad-optimized prompts into artifacts that the strategy engine can load like any other strategy. The evaluation layer parses and scores answers, classifies errors, computes statistics and generates perturbed questions. The presentation layer stores one JSON line per answered question and turns the runs into tables, figures and an interactive web application.

Fig. 2 shows how a single question flows through the system. The same eight stages are used by the experiment runner and by the web application.

5. Data design

Two data classes define the contract between modules. Every loader produces Example objects and every strategy returns a Prediction; experiment.evaluate_example flattens both into one JSON record that is appended to the run file as soon as the question is answered, which makes runs resumable (already-answered question IDs are skipped).

@dataclass
class Example:                 # one question, any dataset
    uid: str; dataset: str; question: str
    table: list                # rows of cell strings; row 0 = header
    texts: list                # sentences / paragraphs
    gold: float | str          # number or "yes"/"no"
    gold_program: str          # FinQA program / TAT-QA derivation / formula
    n_steps: int               # arithmetic operations needed
    evidence: str              # "table" | "text" | "table-text"
    scale: str                 # "percent", "million", "crore", ...
    gold_facts: list           # e.g. ["table_3", "text_5"]

@dataclass
class Prediction:              # what every strategy returns
    answer: float | str | None; how: str      # answer_line / code / vote ...
    output: str; code: str; trace: dict; error: str
    n_calls: int; prompt_tokens: int; completion_tokens: int
    latency: float; extra: dict              # votes, grounding, agreement

Model responses are cached in SQLite (~/.cache/finreason/llm_cache.sqlite) under a SHA-256 key of (model, thinking flag, max tokens, messages, temperature, sample id); write-ahead logging lets the experiment runner and the web app use the cache concurrently. Optimization outputs are stored as JSON artifacts (artifacts/dspy_*.json with a .meta.json describing cost and chosen demos; artifacts/textgrad_*.json with the best prompt and the full optimization history).

6.1 Prompt anatomy

Text strategies use one system prompt, a strategy instruction and the same answer-format rules; Program-of-Thought replaces the rules with a code instruction. Few-shot strategies prepend three worked examples — real FinQA train questions on a percentage change, an average share price from text, and a share computed across units (billion → million) — as earlier user/assistant turns, serialized in the same table format as the test question. A unit test checks that every worked example itself evaluates to its gold answer.

SYSTEM: You are a careful financial analyst. Answer questions about a financial report using only the table and text provided.

ANSWER FORMAT:
Answer format:
- The final answer is a single number. Unless the question asks for another unit, use the same units as the report (if the table says "in millions", answer in millions). Do not write the unit.
- Write percentages as percent numbers (12.5 means 12.5%).
- Use a minus sign for decreases and negative values.
- For yes/no questions, answer yes or no.
- The last line must be: Answer: <number>

DECOMPOSITION: Solve in four labelled parts:
Knowledge: the financial formula or definition needed.
Extract: every value needed, with where it comes from and its units.
Decompose: the calculation as numbered steps, one arithmetic operation per step.
Answer: the final answer.

PROGRAM-OF-THOUGHT: Write Python code that computes the answer. Put each value from the report in a variable with a descriptive name, compute the result step by step, and store the final answer in a variable named ans (a number, or the string 'yes' or 'no'). Keep the report's units unless the question asks otherwise; give percentages as percent numbers (12.5 means 12.5%). Return only the code in one ```python block.

REPAIR: Running your code failed with this error:
{error}
Fix the code and return only the corrected code in one ```python block.

6.2 Answer extraction

The parser removes Markdown/LaTeX decoration and reads, in order of preference, the last Answer: line, a \boxed{} expression, or the last number in the output (counted as a format failure). Numbers may carry currency symbols (₹, $, Rs, INR), Indian or Western digit grouping, bracketed negatives, percent signs and scale words (thousand, lakh, million, crore, billion).

6.3 Verified Program Self-Consistency (VPSC)

Our error analysis of preliminary runs showed that, once arithmetic is delegated to code, most remaining errors are evidence errors: the model uses a number that is not the correct one from the report. VPSC (Fig. 3) samples five programs — the greedy program (identical to the Program-of-Thought call, so it is served from the cache) and four at temperature 0.7 — and executes each in the sandbox. A program is grounded if every numeric literal in its abstract syntax tree occurs in the report, allowing small integers (0–12), unit constants (100, 1,000, 105, 106, 107, 109), years (1900–2100), and the report's numbers rescaled by ×100, ×1000, ÷100 or ÷1000. The answer is the majority vote over executed, grounded programs; if no program is grounded, all executed programs vote. Confidence is the share of the five votes the winner received. The ablation, PoT Self-Consistency, votes over the same five programs without the check, so VPSC − PoT-SC measures the effect of verification alone, and VPSC vs CoT Self-Consistency compares equal budgets (five calls).

7. Sandbox security design

Generated code is untrusted. The sandbox applies four independent layers (Fig. 4): (1) a static AST check that allows only import math and rejects names such as open, eval, exec, os, sys and any dunder attribute; (2) execution in a fresh python -I process (isolated mode: no user site-packages, no environment variables), with the code passed on standard input; (3) a whitelist of safe builtins with print disabled; and (4) a CPU-time resource limit plus a 5-second wall-clock timeout. The child process returns only JSON: the value of ans and all numeric variables, which become the calculation trace shown to the user. On failure, Program-of-Thought shows the error message to the model once and runs the repaired code.

8. Automated optimization design

DSPy [19]: a FinancialQA signature (inputs: context, question; output: answer) with the same answer rules as the manual prompts, wrapped in dspy.ChainOfThought. The optimization metric is our own scorer, so the optimizer maximizes exactly what we report. BootstrapFewShot runs the program on 50 FinQA-train questions and keeps up to three traces the metric marks correct as demonstrations (only self-generated demos, max_labeled_demos = 0). MIPROv2 [20] (light setting) proposes instructions and demo sets and searches over them with minibatch evaluation on 40 FinQA-dev questions. TextGrad [21]: the system prompt of zero-shot CoT is a trainable variable; for each batch of six training questions, only wrongly answered questions produce a loss (“the correct answer is …; identify which step went wrong and which general instruction would have prevented it”); the optimizer model writes the textual gradient and rewrites the prompt under two constraints (keep the Answer: line; stay general). After each of six steps the candidate is kept only if accuracy on 30 FinQA-dev questions does not drop. For the 1.7B model the feedback is written by the 8B model.

9. Retrieval design

By default the model sees the whole page. In retrieval mode, the page is split into evidence units — one per table row (rendered as “label: column = value; …”) and one per sentence — and ranked by BM25 [23] and by cosine similarity of all-MiniLM-L6-v2 embeddings [24] in a FAISS inner-product index [25]; the two rankings are fused with Reciprocal Rank Fusion [26] (k = 60). The context keeps the table header plus the top-k units in document order. Fig. 6 shows recall of the gold evidence units on the full test sets.

10. Evaluation design

Execution accuracy is the primary metric: a numeric prediction is correct if it is within 0.5% of the gold value or equals the gold value rounded to the number of decimals the gold is written with; for percentage questions the ×100 and ÷100 forms are also accepted. Yes/no answers must match exactly. We also report accuracy at 1% tolerance, exact match after rounding both to two decimals, TAT-QA-style token F1, format-failure rate (no Answer: line) and code-failure rate. Cost metrics are LLM calls, prompt and completion tokens, tokens per correct answer and latency per question; optimizers additionally report their one-time compile cost. Each wrong answer receives exactly one error category (Table 2).

Table 2. Error taxonomy (checked in this order).

CategoryRule
no_answerNo parsable answer in the output
execution_errorPoT code failed even after one repair
sign_errorRight magnitude, wrong sign (increase vs decrease)
scale_errorOff by a unit factor: 10², 10³, 10⁵ (lakh), 10⁶, 10⁷ (crore), 10⁹
rounding_near_missWithin 5% but outside the 0.5% tolerance
no_work_shownWrong, with ≤ 1 number in the output (nothing to diagnose)
evidence_errorAt least one gold operand never appears in the model's work
reasoning_errorAll gold operands appear, but the formula or arithmetic is wrong

Uncertainty is reported as 95% percentile-bootstrap confidence intervals [31] (2,000 resamples). Strategies are compared with few-shot CoT on the same questions using the exact McNemar test [30], with Holm correction [33] within each setting, as recommended for NLP [32].

12. Deployment and web-application design

The web application (Streamlit) has five pages. Ask runs the full pipeline live on a dataset question, a pasted table or a page of an uploaded PDF, and shows the pipeline stages, an answer card with confidence, highlighted evidence rows, the generated code and variable trace, the votes (with grounding) and the exact prompt. Compare runs several strategies on one question side by side with token costs. Results shows interactive charts, significance tests and figures from the experiment runs. Error explorer lists every wrong answer by strategy and category with its reasoning. About explains the method. Fig. 8 shows the sequence of one request.

13.2 The Indian annual-report set (new)

Motivation. Public benchmarks contain only US filings. Indian reports express amounts in ₹ crore and lakh (1 crore = 100 lakh = 10 million), use Indian digit grouping (1,00,000), write negatives in brackets, follow Ind AS layouts and distinguish standalone from consolidated statements. The questions are new (written by us) over reports published in 2024–25, so the question–answer pairs cannot have been memorized from public benchmarks.

13.3 Derived data: numerically perturbed FinQA

To test memorization (cf. GSM-Symbolic [28]), perturb.py rewrites each sampled FinQA question: every literal operand of the gold program is multiplied by a random factor from [0.7, 0.9] ∪ [1.1, 1.3] (seed 42) with its original number of decimals; all occurrences in the table and text are replaced in a single pass; and the new gold answer is obtained by executing the rewritten gold program with our FinQA program interpreter. Questions are skipped when an operand is a year, a percentage or negative, when it does not appear verbatim in the report, or when the program fails — leaving 88 of the 100 questions. Example (STT 2009, p. 127): subtract(368, 68) = 300 becomes subtract(272, 82) = 190.

14. Data quality and verification

  • Indian set — independent re-check (performed for this review). We re-extracted the text of every cited PDF page with pdfplumber and checked, for each question, that every operand of its formula occurs on the cited page, then inspected the PDF line containing each operand to confirm it is the intended row and year column, and recomputed the gold answer from the formula. Result: 44/44 questions have all operands on their cited pages and 44/44 gold answers match exactly (results/indian_verification.csv). Two return-on-equity questions use profit from the P&L page (adjacent to the cited balance-sheet page), which the question text also states.
  • FinQA gold programs: a unit test re-executes the gold program of all 1,147 FinQA test questions with our interpreter and reproduces every published answer; the three worked examples are tested to produce their gold answers.
  • No leakage: worked examples and optimization data come only from FinQA train/dev; the test samples are fixed by seed and never used for tuning.
  • Known label noise: some FinQA gold answers are themselves wrong (e.g. the direction of a change), which caps reachable accuracy; we keep the official labels.
  • Remaining step: a human sign-off of the verification checklist by a team member (opening each PDF page) before the final report.
