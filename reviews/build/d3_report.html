Abstract

Financial reports mix tables and narrative text, and analytical questions over them require locating evidence, extracting values with the right units, scale and sign, applying domain formulas and multi-step arithmetic. We present FinReason, a controlled, cost-aware study and system for this task. On FinQA, the arithmetic subset of TAT-QA and a new set of 44 questions over four Indian annual reports (₹ crore/lakh), we compare six hand-written prompting strategies, automated prompt optimization (DSPy BootstrapFewShot and MIPROv2, TextGrad) and a new method, Verified Program Self-Consistency (VPSC), which rejects generated programs that use numbers not found in the report before voting. All models run locally (Qwen3-1.7B and Qwen3-8B via Ollama). With Qwen3-1.7B, direct answering reaches at most 11%, while reasoning strategies reach 57% on FinQA, 74% on TAT-QA and 77% on the Indian set; Program-of-Thought is the best single-call strategy on FinQA and Indian reports (CoT few-shot on TAT-QA), and five-sample strategies cost 4.4–5.0× the tokens of few-shot CoT without significant gains. Error analysis shows that most remaining errors are evidence errors (wrong or missing operands). The grounding check flags such answers precisely but, for the small model, rarely changes the vote. A Streamlit application exposes the full pipeline with evidence, code, trace and votes for every answer.

1. Introduction

Large Language Models are fluent in financial language but unreliable at numerical reasoning over reports: the best fine-tuned FinQA model reached 61.24% execution accuracy against 91.16% for experts [1], and GPT-4-Turbo with retrieval failed on 81% of evaluated FinanceBench questions [5]. Prompting techniques such as Chain-of-Thought [10], Self-Consistency [12] and Program-of-Thought [15], and prompt optimizers such as DSPy [19], MIPROv2 [20] and TextGrad [21] promise cheap improvements, but we found no study that compares them under one controlled, cost-aware protocol on financial table-text reasoning with small local models. Recent work verifies a model's numbers against structured filing data with a solver [38] or with a trained evidence-auditing agent [39], and recent Indian financial benchmarks cover filing look-up [36] and regulatory text [37]. This report describes the implementation (Section 2), the experimental setup (Section 3), the results (Section 4), the web application (Section 5), and discusses findings, limitations and future work (Sections 6–7). Reviews 1 and 2 contain the full literature survey and the high-level design.

Contributions

  • A reproducible benchmark of 11 prompting strategies on three datasets with accuracy, confidence intervals, paired significance tests, token cost and latency.
  • VPSC, a training-free grounding check inside program self-consistency (lighter than solver- or training-based verifiers [38], [39]), with an exactly matched ablation.
  • An Indian annual-report test set of 44 multi-step calculation questions (₹ crore/lakh) with formula-computed, PDF-verified gold answers, complementing look-up benchmarks [36].
  • An error taxonomy, a numerical-perturbation memorization test and ablations on table format, retrieval and thinking mode.
  • An auditable web application.

2. Implementation

FinReason is a Python 3.13 library (finreason/, 19 modules, about 1,900 lines) with command-line scripts, a Streamlit application and 58 automated tests (all passing). Fig. 1 shows the architecture; the design is documented in the Review 2 report.

  • Strategies share one interface strategy(llm, example, context, fmt) → Prediction: direct, zero-/few-shot CoT, decomposition (after EEDP [8]), Program-of-Thought with one repair round, CoT Self-Consistency (5 samples), PoT Self-Consistency and VPSC (Fig. 2); DSPy-compiled programs and TextGrad prompts are loaded from artifacts with the same interface.
  • Sandbox: AST checks, isolated python -I process, whitelisted builtins, CPU and wall-clock limits.
  • Grounding verifier: every numeric literal in a program must occur in the report (allowing unit rescaling and harmless constants).
  • Evaluation: answer parser for Indian and Western number formats, scorer, rule-based error taxonomy, bootstrap CIs, McNemar + Holm.
  • Engineering: one LLM client for Ollama and API providers with a SQLite response cache; resumable JSONL run files; analysis re-scores all runs.

4.2 Key findings

  • Showing work is essential. Direct answering reaches only 2–11%; the best reasoning strategy reaches 57% (Program-of-Thought) on FinQA, 74% (Self-Consistency) on TAT-QA, 77% (Program-of-Thought) on Indian reports.
  • Program-of-Thought vs few-shot CoT: FinQA +5 pts (Holm p = 1.000); TAT-QA -6 pts (Holm p = 1.000); Indian reports +11 pts (Holm p = 1.000). None of these differences is significant after Holm correction — with 44–100 questions only large effects can be detected.
  • Self-Consistency is poor value for a small model: five CoT samples change accuracy by -1 pts on FinQA, +1 pts on TAT-QA, +0 pts on Indian reports at about 5.0× the tokens of one few-shot CoT call — none of these differences is significant.
  • VPSC (ours): the grounding check rejected 26 of 1203 executed programs (2.2%), touching 6 questions; 6 of these 6 questions were answered wrongly. Because the five samples agree strongly (mean vote agreement 91% on FinQA, 97% on TAT-QA, 99% on Indian reports) and in 5 of the 6 flagged questions all programs were ungrounded (so the fallback vote was used), verification changed no final answer: VPSC = PoT-SC. The check is therefore most useful as a reliability flag (an ungrounded answer is very likely wrong) rather than as a vote filter for this model.
  • Evidence errors dominate: across reasoning strategies on FinQA and TAT-QA, 60% of the 549 wrong answers use a wrong or missing operand, 23% have all operands but a wrong formula/arithmetic, 9% are unit/scale errors and 4% sign errors. The bottleneck is finding and copying the right numbers, not computing.
  • Generalization to Indian reports: CoT few-shot 66% (FinQA 52%), Program-of-Thought 77% (FinQA 57%), VPSC (ours) 77% (FinQA 56%) on the 44 ₹ crore/lakh questions — at or above the FinQA level, so the strategies transfer to unseen, region-specific statements.
  • Automated optimization: DSPy BootstrapFewShot FinQA 45% (-7 vs few-shot CoT); TextGrad FinQA 43% (-9 vs few-shot CoT); TextGrad TAT-QA 60% (-13 vs few-shot CoT); TextGrad Indian reports 68% (+2 vs few-shot CoT).
  • Perturbed numbers: on the same FinQA questions with changed numbers, CoT few-shot 56% → 50% (n = 88, McNemar p = 0.424); Program-of-Thought 58% → 56% (n = 88, McNemar p = 0.754); VPSC (ours) 57% → 55% (n = 88, McNemar p = 0.754). No drop is significant, so there is no evidence that the model answers from memorized FinQA answers.

Qwen3-8B:

  • Showing work is essential. Direct answering reaches only 37–37%; the best reasoning strategy reaches 75% (CoT zero-shot) on FinQA.
  • Program-of-Thought vs few-shot CoT: FinQA +3 pts (Holm p = 1.000). None of these differences is significant after Holm correction — with 44–100 questions only large effects can be detected.
  • Self-Consistency is poor value for a small model: five CoT samples change accuracy by +3 pts on FinQA at about 5.0× the tokens of one few-shot CoT call — none of these differences is significant.
  • Evidence errors dominate: across reasoning strategies on FinQA and TAT-QA, 34% of the 136 wrong answers use a wrong or missing operand, 37% have all operands but a wrong formula/arithmetic, 9% are unit/scale errors and 10% sign errors. The bottleneck is finding and copying the right numbers, not computing.

Final TextGrad system prompt (Qwen3-1.7B):

You are a careful financial analyst. Answer questions about a financial report using only the table and text provided. Always check the units of the values. If the question asks for the answer in millions, convert all values to millions before performing calculations. Follow these steps: (1) Rephrase the question in your own words to ensure complete understanding of what is being asked. (2) Identify the relevant numbers from the table and text. (3) Check the units of the values (e.g., in thousands, in millions). (4) Convert units as needed to match the question's requested scale. (5) Perform the calculation with unit consistency. (6) Verify that the final answer is in the correct unit and scale as specified in the question. Unless the question asks for another unit, use the same units as the report (if the table says "in millions", answer in millions). Be cautious of values presented in thousands or millions. Always follow the unit instruction in the question. When calculating percentage change, ensure that the sign of the result reflects the direction of change: a negative value indicates a decrease, and a positive value indicates an increase. Use the formula: $$
\text{Percentage Change} = \frac{\text{New Value} - \text{Old Value}}{\text{Old Value}} \times 100
$$ The sign of the result indicates the direction of change, and the absolute value represents the magnitude of the change. Always provide a step-by-step explanation of your reasoning. If the data does not provide the necessary granularity (e.g., monthly, quarterly, or per-transaction) to answer the question, clearly state that the calculation cannot be performed and explain why the data is insufficient. Ensure that the final answer is precise and unambiguous. If the question asks for a percentage, always present the result as a percentage, not a decimal. If an arithmetic error occurs during the calculation, clearly identify the step where the error occurred, and explain how rounding or miscalculation affected the final result. Avoid rounding intermediate values until the final step to prevent cumulative errors. Always carry out calculations with full precision, and only round the final result to the required decimal places. If you encounter an unexpected result, trace the error back to the exact step where it occurred. This includes checking the arithmetic, unit conversions, and formula application. After completing the calculation, clearly state the final answer and explain how it was derived. If any corrections were made for errors, explicitly state the nature of the error and how it was resolved. If the data does not provide the necessary categorization (e.g., SG&A vs. cost of sales) to answer the question, clearly state that the calculation cannot be performed and explain what specific information is missing. If the question asks for a change in basis points, remember that a basis point is 0.01%, so multiply the percentage change by 100 to convert it to basis points. Always verify the unit of the answer based on the question's wording. The last line must be: Answer: <number>

4.10 Generalization to Indian annual reports

Generalization to Indian reports: CoT few-shot 66% (FinQA 52%), Program-of-Thought 77% (FinQA 57%), VPSC (ours) 77% (FinQA 56%) on the 44 ₹ crore/lakh questions — at or above the FinQA level, so the strategies transfer to unseen, region-specific statements.

The Streamlit application runs the complete pipeline on a dataset question, a pasted table or a page of an uploaded PDF and shows each stage, the answer with its confidence, the evidence rows used, the generated code with its variable trace, the votes with grounding status and the exact prompt (Fig. 8). The Compare, Results, Optimization, Robustness, Errors and Data pages expose the experiments, and the Overview page checks every claim against the project. 6. Answers to the research questions

RQAnswer
RQ1 — strategiesVery much at the low end, little at the top. Moving from direct answering to any reasoning strategy raises Qwen3-1.7B from ≤11% to 44–77%. Among reasoning strategies the differences are a few points and none is significant after Holm correction; the best per dataset is Program-of-Thought on FinQA (57%), Self-Consistency on TAT-QA (74%), Program-of-Thought on Indian reports (77%). Fewest tokens per correct answer: CoT zero-shot on FinQA (2,614), CoT zero-shot on TAT-QA (1,259), CoT zero-shot on Indian reports (1,306); five-sample strategies cost 4.4–5.0× the tokens of few-shot CoT.
RQ2 — automated optimizationDSPy BootstrapFewShot on FinQA: 45% (zero-shot CoT 49%, few-shot CoT 52%); TextGrad on FinQA: 43% (zero-shot CoT 49%, few-shot CoT 52%); TextGrad on TAT-QA: 60% (zero-shot CoT 68%, few-shot CoT 73%); TextGrad on Indian reports: 68% (zero-shot CoT 66%, few-shot CoT 66%). One-time optimization costs are given in the optimization table.
RQ3 — model sizeCoT few-shot FinQA 52 → 70%; Program-of-Thought FinQA 57 → 73%.
RQ4 — failures and robustnessMost errors are evidence errors (60% of 549 wrong answers of reasoning strategies), followed by reasoning (23%) and scale/unit errors (9%). Accuracy on the unseen Indian reports (Program-of-Thought 77%) is not lower than on FinQA, so the strategies generalize to ₹ crore/lakh statements. Perturbation: CoT few-shot 56% → 50% (p = 0.424); Program-of-Thought 58% → 56% (p = 0.754); VPSC (ours) 57% → 55% (p = 0.754).
RQ5 — verification (VPSC)Not for Qwen3-1.7B as a vote filter: VPSC and PoT-SC have identical accuracy on all three datasets, because the five sampled programs rarely disagree and ungrounded programs usually appear in all five samples. However, every question the check flagged (6 in total) was answered wrongly, so grounding is a precise signal for flagging unreliable answers to a human.

7. Limitations and future work

  • Sample size. 100/100/44 questions give CIs of about ±10 points; only large differences are certain. Paired tests partly compensate; the code supports full test sets.
  • Models. One family (Qwen3, 4-bit, local). API models are supported by the client but were not run.
  • Indian set. Small and authored by us; gold answers are formula-computed and independently re-verified against the PDFs (44/44), but question style follows our design.
  • Error taxonomy is rule-based (operand matching) rather than human-annotated.
  • Grounding verifies that a number occurs in the report, not that it is the intended cell; a wrong-year value passes.
  • FinQA label noise caps attainable accuracy; latency was measured under parallel load.

Future work: cell-aware grounding (row and column, not only value) with abstention; larger and API models and more diverse samplers for VPSC; full test sets and human error annotation; retrieval over complete annual reports.

8. Conclusion

Prompting matters most at the bottom: for a 1.7B local model, asking for reasoning or a program turns a near-useless model into a usable one, while the differences between good strategies are small and mostly not significant on 100-question samples. Program-of-Thought is the most cost-effective strong strategy for exact financial arithmetic; spending five samples rarely pays off for a small model. The dominant remaining error is evidence selection, which grounding verification can flag precisely; making that flag cell-aware and using it for abstention is the most promising next step. FinReason makes every answer auditable and every result reproducible.
