5. Numbers to remember

  • Showing work is essential. Direct answering reaches only 2–11%; the best reasoning strategy reaches 57% (Program-of-Thought) on FinQA, 73% (CoT few-shot) on TAT-QA, 77% (Program-of-Thought) on Indian reports.
  • Program-of-Thought vs few-shot CoT: FinQA +5 pts (Holm p = 1.000); TAT-QA -6 pts (Holm p = 1.000); Indian reports +11 pts (Holm p = 1.000). None of these differences is significant after Holm correction — with 44–100 questions only large effects can be detected.
  • Self-Consistency is poor value for a small model: five CoT samples change accuracy by +1 pts on FinQA, -1 pts on TAT-QA, +0 pts on Indian reports at about 5.0× the tokens of one few-shot CoT call — none of these differences is significant.
  • VPSC (ours): the grounding check rejected 26 of 1203 executed programs (2.2%), touching 6 questions; 6 of these 6 questions were answered wrongly. Because the five samples agree strongly (mean vote agreement 91% on FinQA, 97% on TAT-QA, 99% on Indian reports) and in 5 of the 6 flagged questions all programs were ungrounded (so the fallback vote was used), verification changed no final answer: VPSC = PoT-SC. The check is therefore most useful as a reliability flag (an ungrounded answer is very likely wrong) rather than as a vote filter for this model.
  • Evidence errors dominate: across reasoning strategies on FinQA and TAT-QA, 60% of the 549 wrong answers use a wrong or missing operand, 23% have all operands but a wrong formula/arithmetic, 9% are unit/scale errors and 5% sign errors. The bottleneck is finding and copying the right numbers, not computing.
  • Generalization to Indian reports: CoT few-shot 66% (FinQA 52%), Program-of-Thought 77% (FinQA 57%), VPSC (ours) 77% (FinQA 56%) on the 44 ₹ crore/lakh questions — at or above the FinQA level, so the strategies transfer to unseen, region-specific statements.
  • Perturbed numbers: on the same FinQA questions with changed numbers, CoT few-shot 56% → 50% (n = 88, McNemar p = 0.424); Program-of-Thought 58% → 56% (n = 88, McNemar p = 0.754); VPSC (ours) 63% → 61% (n = 49, McNemar p = 1.000). No drop is significant, so there is no evidence that the model answers from memorized FinQA answers.

6. Likely viva questions

Q1. What exactly is the task?

Given one report page (table + text) and a question that needs arithmetic, output the number (or yes/no). We score with execution accuracy: within 0.5% of the gold value, or equal at the gold's precision; percent and fraction forms both accepted.

Q2. Why not just fine-tune a model?

Fine-tuning needs labelled data, GPUs and retraining for every new model. Prompting and prompt optimization are cheap, model-agnostic and the course focus; TAT-LLM and BloombergGPT show the training route but at much higher cost.

Q3. Why Program-of-Thought?

LLMs are bad at exact multi-digit arithmetic. In PoT the model only decides what to compute; Python computes it exactly. In our results with Qwen3-1.7B: Program-of-Thought is the best single-call strategy on FinQA and Indian reports (CoT few-shot on TAT-QA).

Q4. What is VPSC and what is new about it?

Five PoT programs are sampled and executed; programs that use a number not found in the report are discarded before the majority vote. The grounding check is new; PoT-SC uses the same five programs without it, so the comparison isolates verification exactly.

Q5. Did VPSC beat PoT-SC?

Not for Qwen3-1.7B: accuracy is identical because the five samples nearly always agree and ungrounded programs appear in all samples. But every flagged question was wrong, so the check is a precise reliability signal — useful for abstention or alerts.

Q6. Why McNemar's test?

All strategies answer the same questions, so results are paired. McNemar uses only the discordant questions (one right, the other wrong) and is exact via the binomial distribution. Holm corrects for testing many strategies.

Q7. Why are your confidence intervals so wide?

With n = 100 a 95% CI is about ±10 points. We report CIs honestly and rely on paired tests; the code can run full test sets (--n 0) with more compute.

Q8. How do you avoid test leakage?

Worked examples and all DSPy/TextGrad training data come from FinQA train/dev; test samples are fixed by seed and never used for tuning.

Q9. How did you build the Indian set and why trust it?

Tables were transcribed from official PDFs; every one of the 366 cells must appear on its PDF page or the build fails; gold answers are computed by running formulas, never typed; and we independently re-extracted every page and confirmed all 44 questions' operands and gold values.

Q10. What is the numerical perturbation test?

We change every operand of the FinQA gold program by 10–30%, replace it in the table/text and recompute the gold with the program. A model that memorized FinQA answers would fail; a reasoning model should not care.

Q11. How is the code sandbox safe?

Four layers: AST rules (only math import, no dunders, no open/eval/os), a fresh isolated python -I process, whitelisted builtins, and CPU + 5 s time limits. Output is JSON only.

Q12. What does DSPy actually optimize?

A ChainOfThought program with our FinancialQA signature. BootstrapFewShot keeps up to three self-generated traces that our metric marks correct as demos; MIPROv2 also proposes instructions and searches combinations with a Bayesian surrogate on dev minibatches.

Q13. What does TextGrad optimize?

The system prompt of zero-shot CoT. Wrong answers get a critique (a ‘textual gradient’) from the optimizer model; TGD rewrites the prompt; we keep the update only if dev accuracy does not drop.

Q14. Why is Self-Consistency not helping?

For a 1.7B model at T = 0.7 the samples mostly repeat the same reasoning, so the vote rarely changes the answer, while costing five times the tokens.

Q15. What are the main error types?

Evidence errors dominate: a needed operand is missing or wrong. Then reasoning errors (right numbers, wrong formula), scale/unit errors and sign errors. Direct answering mostly shows no work.

Q16. Why two Ollama servers?

The experiments keep one server busy for hours; the app uses a second server so live questions are not queued behind experiments.

Q17. Why cache responses?

Identical requests return instantly and identically; experiments are resumable; VPSC's first sample reuses the PoT call, so the ablation costs nothing extra.

Q18. What would you do with more time?

Cell-aware grounding (check the right row and column) and abstention; larger/API models; full test sets; retrieval over whole annual reports.

Q19. What are the limitations?

Small samples, one model family, a small self-written Indian set, a heuristic error taxonomy, value-level grounding, FinQA label noise, latency measured under parallel load.

Q20. How do you know the scorer is right?

Unit tests cover parsing (Indian grouping, brackets, %, scale words), tolerance and percent/fraction handling; the same scorer is used at run time, in DSPy's metric, in TextGrad validation, in the app and in the analysis, which re-scores everything.
