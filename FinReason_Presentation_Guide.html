01The project in one minute

The problem. Financial reports are full of tables. Questions like “what was the percentage change in revenue?” need four skills: find the right row and year, read the number with its unit and sign, choose the right formula, and do the arithmetic. One wrong digit, unit or sign gives a confident wrong answer.

The question we ask. How do prompting strategies and automatic prompt optimizers change the accuracy, cost and reliability of small, local LLMs on these questions? We change only the prompt, never the model (no fine-tuning).

What we built.

  • 7 hand-written prompting strategies: Direct, zero-shot Chain-of-Thought, few-shot CoT, Decomposition, Program-of-Thought, Self-Consistency, and our method VPSC.
  • VPSC (Verified Program Self-Consistency), our method: the model writes 5 Python programs, a sandbox runs each, programs that use a number that is not in the report are thrown out, and the rest vote.
  • 3 automatic prompt optimizers: DSPy BootstrapFewShot, DSPy MIPROv2 and TextGrad (MIPROv2 is implemented but its run did not finish; see section 07).
  • 2 local models: Qwen3-1.7B and Qwen3-8B, run with Ollama on an Apple M4 laptop.
  • 3 test sets: FinQA (100 questions), TAT-QA (100) and our own Indian annual-report set (44 questions over Titan, Asian Paints, Marico and Pidilite, in ₹ crore).
  • A full evaluation: accuracy with 95% confidence intervals, paired significance tests, cost in tokens, error taxonomy, memorization test and ablations.
  • A web app where every answer can be audited: evidence rows, code, votes, grounding and the exact prompt.
Say this · the three findings

1) Asking the model to reason matters most: answer-only prompts get at most 11% with the 1.7B model; any reasoning strategy gets 44–77%. 2) Letting Python do the arithmetic (Program-of-Thought) is the best single-call strategy on FinQA and our Indian set. 3) The remaining errors are mostly about picking the wrong number from the report (60% of wrong answers), not about arithmetic. Our grounding check flags such answers precisely: every question it flagged was wrong.

02Concepts from scratch

LLM, prompt, tokens

A large language model predicts the next piece of text, one token at a time (a token is roughly ¾ of a word; numbers often split into several tokens). A prompt is everything we send: a system message (the role and rules), optional earlier user/assistant turns (worked examples), and the user message (the report context plus the question). Cost is measured in tokens: prompt tokens (what we send) plus completion tokens (what the model writes).

Temperature, greedy decoding, seeds

At each step the model has a probability for every next token. Temperature 0 (greedy) always takes the most likely one, so the same prompt gives the same answer. Temperature 0.7 samples, so repeated calls give different reasoning paths. We fix the random seed (42 + sample number) so even sampled runs are reproducible.

Why Chain-of-Thought works: the model writes intermediate steps, so each next token depends on numbers it has already written down. It acts like a scratchpad. Without it, the model must “compute in its head” in one token, which small models cannot do.

Why Program-of-Thought works: LLMs are bad at exact multi-digit arithmetic (e.g. 3338 − 4273 = −935, then ÷ 4273). In PoT the model only decides what to compute; Python computes it exactly. This idea comes from Chen et al., “Program of Thoughts Prompting” (TMLR 2023).

Why Self-Consistency works: different sampled reasoning paths make different mistakes, but the correct answer tends to be the most common one (Wang et al., 2023). The cost is 5× the calls.

Automatic prompt optimization

  • DSPy (Stanford) treats a prompt as a program. You declare a signature (inputs context, question → output answer) and a module (ChainOfThought). An optimizer then chooses the instruction and the few-shot demonstrations automatically, using a metric.
  • BootstrapFewShot: runs the program on training questions and keeps up to 3 runs the metric marks correct as demonstrations (the model’s own reasoning in its own words).
  • MIPROv2: an LLM proposes candidate instructions; Bayesian optimization (Optuna) searches over (instruction, demo set) pairs, scoring each on validation questions.
  • TextGrad (Stanford, 2024): “automatic differentiation with text”. The system prompt is a trainable variable. For each wrong answer an LLM writes a critique (a “textual gradient”: what went wrong and what instruction would prevent it), and an optimizer LLM rewrites the prompt using those critiques. In our setup the 8B model writes the critiques for the 1.7B model’s prompt.

Retrieval (finding the evidence)

  • Evidence unit: one table row (turned into a sentence) or one text sentence.
  • BM25: classic keyword search. Scores a unit higher when it shares rare words with the question, with diminishing returns for repeated words and a correction for long units.
  • Dense retrieval: a sentence-embedding model (all-MiniLM-L6-v2, 384-dimensional vectors) turns text into vectors; similar meanings get similar vectors. We compare with cosine similarity using FAISS (IndexFlatIP, exact inner-product search on normalized vectors, which equals cosine).
  • Reciprocal Rank Fusion (RRF): combine the two rankings. Each unit gets Σ 1 / (60 + rank) over both rankings (rank starts at 1). It needs no score calibration, only ranks.
  • Recall@k: the fraction of gold evidence units that appear in the top k.

Running models locally

Ollama is a local server for open-weight models with an HTTP API (default port 11434; our app uses its own on 11435). Our models are Qwen3-1.7B (2.0 B parameters) and Qwen3-8B (8.2 B), both Q4_K_M quantized (weights stored in about 4 bits, so the 8B fits in laptop memory). Qwen3 has a built-in thinking mode that writes hidden reasoning in <think>…</think>; we turn it off by default and test it as an ablation.

Evaluation and statistics

  • Execution accuracy (our main metric): correct if within 0.5% of the gold number, or equal when rounded to the gold’s own decimals. For percentage questions, 12.5 and 0.125 are both accepted (FinQA stores percentages as fractions).
  • Exact match (EM): prediction and gold equal when both are rounded to 2 decimals. F1: TAT-QA’s token F1; for single numbers it equals EM.
  • 95% bootstrap confidence interval: resample the 100 right/wrong flags with replacement 2,000 times, compute accuracy each time, take the 2.5th and 97.5th percentiles. With 100 questions the interval is about ±10 points.
  • McNemar’s test: for two strategies on the same questions, count only the questions where they disagree: b (A right, B wrong) and c (A wrong, B right). If both are equally good, b follows Binomial(b + c, 0.5). We use the exact binomial version.
  • Holm–Bonferroni correction: we test many strategies against one baseline, so some small p-values would appear by luck. Holm sorts the p-values and multiplies the smallest by m, the next by m − 1, and so on (keeping them increasing), which controls the chance of any false positive.

def retrieve(self, question, units, k=5, method="hybrid"):
    texts = [text for _, text in units]
    rankings = []
    if method in ("bm25", "hybrid"):
        rankings.append(self.bm25_ranking(question, texts))
    if method in ("dense", "hybrid"):
        rankings.append(self.dense_ranking(question, texts))
    fused = np.zeros(len(units))
    for ranking in rankings:
        for rank, idx in enumerate(ranking):
            fused[idx] += 1.0 / (self.rrf_k + rank + 1)      # RRF, rrf_k = 60
    best = np.argsort(-fused, kind="stable")[:k]
    return [(units[i][0], units[i][1], float(fused[i])) for i in best]

build_context(example, fmt, mode, retriever, k) makes the text the model sees. In mode="full" it is the whole table plus all text. LLM client and cache · llm.py

One class talks to Ollama, OpenAI-compatible APIs (OpenAI, Groq, Gemini, OpenRouter) and Anthropic. A model is named provider:model, e.g. ollama:qwen3:8b.

finreason/llm.py
def chat(self, messages, temperature=0.0, sample_id=0):
    request = [self.spec, self.think, self.max_tokens, messages, temperature, sample_id]
    key = hashlib.sha256(json.dumps(request).encode()).hexdigest()
    if self.cache and (hit := self.cache.get(key)):
        return LLMResponse(**hit, cached=True)              # same request → same stored answer
    start = time.perf_counter()
    for attempt in range(3):
        try:
            text, n_in, n_out = self._call(messages, temperature, sample_id)
            if not text and n_in == 0 and n_out == 0:       # GPU out of memory etc.
                raise RuntimeError("... returned an empty response (server error)")
            break
        except Exception:
            if attempt == 2: raise
            time.sleep(2 ** attempt * 5)                    # back off 5 s, 10 s
    latency = time.perf_counter() - start
    text = re.sub(r"<think>.*?</think>", "", text, flags=re.DOTALL).strip()
    self.cache.put(key, {"text": text, "prompt_tokens": n_in, "completion_tokens": n_out, "latency": latency})
    return LLMResponse(text, n_in, n_out, latency)
  • The cache is a SQLite table at ~/.cache/finreason/llm_cache.sqlite (outside iCloud, which locks open databases). The key is a SHA-256 hash of everything that affects the answer. This makes runs resumable and re-running a finished experiment instant. It also stores the original latency, so timing numbers stay honest.
  • WAL mode lets several programs read and write at once; one lock protects the shared connection across threads.
  • For Ollama, options sets temperature, seed = 42 + sample_id, context window num_ctx = 8192 and output limit num_predict = 1024. Token counts come from Ollama’s prompt_eval_count and eval_count.
  • cost_usd gives dollars for API models with a known price; local models cost 0.

Sandbox · sandbox.py

Model-written code is untrusted, so it runs behind four independent layers:

  1. Static check (AST): parse the code without running it; reject any import other than math, any attribute starting with _ (blocks tricks like ().__class__.__bases__), and names like open, exec, eval, getattr, os, sys, subprocess.
  2. Separate process: a fresh python -I (isolated mode: ignores environment variables and user site-packages). A crash cannot affect the main program.
  3. Restricted builtins: the code runs with a whitelist (abs, min, max, round, sum, len, range, float, int, ...); __import__ only returns math; print does nothing.
  4. Time limits: 5-second timeout and an operating-system CPU limit (RLIMIT_CPU).

def code_literals(code):        # every number typed into the code, via the AST
    return [abs(node.value) for node in ast.walk(ast.parse(code))
            if isinstance(node, ast.Constant) and isinstance(node.value, (int, float))
            and not isinstance(node.value, bool)]

def is_grounded(value, report_numbers):
    if value in CONSTANTS or (float(value).is_integer() and 1900 <= value <= 2100):   # years
        return True
    for n in report_numbers:
        for factor in SCALE_FACTORS:                 # 1.1 (billion) may become 1100 (million)
            if abs(value - n * factor) <= 1e-6 * max(1.0, abs(n * factor)):
                return True
    return False

def grounding_check(code, context):
    report_numbers = {abs(n["value"]) for n in find_numbers(context)}
    missing = [v for v in code_literals(code) if not is_grounded(v, report_numbers)]
    return not missing, missing

def gold_forms(gold, question="", scale=""):
    places = _decimals(gold)
    forms = [(gold, places)]
    if allows_percent(question, scale):      # "percent", "ratio", "margin", "growth", ... in the question
        forms += [(gold * 100, max(0, places - 2)), (gold / 100, places + 2)]
    return forms

def score(pred, gold, question="", scale="", rel_tol=REL_TOLERANCE):   # 0.005 = 0.5%
    if pred is None: return False, False
    if isinstance(gold, str) or isinstance(pred, str):                 # yes / no
        same = isinstance(gold, str) and isinstance(pred, str) and pred == gold
        return same, same
    for g, d in gold_forms(gold, question, scale):
        within_tolerance |= abs(pred - g) <= rel_tol * abs(g)          # (g == 0: |pred| ≤ 0.005)
        if places >= 1:
            rounded_match |= _round(pred, d) == _round(g, d)           # same at the gold's precision
        exact |= _round(pred, 2) == _round(g, 2)
    return within_tolerance or rounded_match or exact, exact

Example: FinQA gold −0.21882 for a percentage question. The forms are −0.21882, −21.882 and −0.0021882. A model answer of −21.88 is within 0.5% of −21.882, so it is correct. Rounding uses Python’s Decimal with ROUND_HALF_UP so 2.675 rounds to 2.68 (plain floats would give 2.67).

Every wrong answer gets exactly one category, checked in this order (the first rule that matches wins):

Perturbation test · perturb.py, finqa_program.py

Question: did the model memorize FinQA answers during pre-training? FinQA is public, so this is possible. Test: change the numbers, recompute the true answer, and see whether accuracy drops.

  1. Take the literal numbers in the FinQA gold program (e.g. 5829 and 5735 in subtract(5829, 5735)).
  2. Multiply each by a random factor in 0.7–0.9 or 1.1–1.3, keeping its decimal places.
  3. Replace every occurrence in the table and text in one pass (both 1234.5 and 1,234.5 forms), so a new number is never replaced again.
  4. Rewrite the program with the new numbers and execute it with finqa_program.execute to get the new gold answer.
  5. Skip a question (return None) if it uses a table operation, a year, a percent or negative argument, or a number not written in the report. 88 of 100 survive.

finqa_program.execute runs FinQA’s little language: add, subtract, multiply, divide, exp, greater, #0 refers to step 0’s result, const_100 is 100, and table_sum/max/min/average work on a table row.

The findings, one by one

1. Reasoning is essential

Direct answering scores 2–11% with the 1.7B model and 37% with the 8B. Every reasoning strategy is far higher (44–77%). Direct vs few-shot CoT is the only difference that survives Holm correction on every dataset (p_holm ≈ 0). The bigger model helps most where there is no reasoning (+32 points on Direct).

2. Python does the arithmetic best, but differences among reasoning strategies are small

PoT is the best single call on FinQA (57%) and Indian (77%); few-shot CoT on TAT-QA (73%). None of these differences is significant after correction. A nice detail: PoT’s exact match is almost equal to its accuracy (FinQA EM 56% vs accuracy 57%), while CoT’s EM is far lower (32% vs 52%), because text reasoning rounds intermediate values and Python does not.

3. Five samples do not pay for a small model

Self-Consistency, PoT-SC and VPSC use 4.4–5.0× the tokens of few-shot CoT for −6 to +11 points, none significant. The samples almost always agree (VPSC agreement: FinQA 91%, TAT-QA 97%, Indian 99%), so voting rarely changes the answer.

4. Errors are about evidence

For Qwen3-1.7B on FinQA + TAT-QA (reasoning strategies, 549 wrong answers): 60% evidence errors (a gold operand is missing from the work, i.e. wrong or missing number), 23% reasoning errors (wrong formula), 9% scale errors (units). So the bottleneck is reading the right number, not arithmetic. With the 8B model the share of evidence errors falls sharply (FinQA few-shot CoT: 31 evidence errors for 1.7B vs 11 for 8B).

6. Generalization to Indian reports

PoT gets 77% on our Indian set vs 57% on FinQA, despite ₹ crore units, Indian number formatting and bigger tables (18 rows on average). Likely reasons: our tables are clean transcriptions and our questions state the period and unit clearly; FinQA has noisy text and some ambiguous questions.

7. No sign of memorization

On the 88 perturbed FinQA questions: few-shot CoT 56 → 50% (p = 0.42), PoT 58 → 56% (p = 0.75), VPSC 57 → 55% (p = 0.75). No significant drop, so the model is reasoning over the numbers it sees, not recalling memorized answers. (The “original” accuracy here is on the same 88 questions, which is why it differs slightly from the 100-question numbers.)

The task and the idea

What exactly is the task?

Given one page of a financial report (a table plus surrounding text) and a question that needs arithmetic, output the number (or yes/no). Scored by execution accuracy: within 0.5% of the gold value, or equal at the gold’s precision; percent and fraction forms both accepted.

Why is this hard for an LLM?

It needs four skills at once: find the right row and column among many similar ones, read the value with unit, scale and sign (brackets mean negative, “in crore”), choose the correct financial formula, and do exact multi-digit arithmetic. LLMs are weak at the last one and small models struggle with the first.

Why not fine-tune a model?

Fine-tuning needs labelled data, GPUs and retraining for every new model. Prompting and prompt optimization are cheap, work with any model, and are the focus of this course. Papers like TAT-LLM and BloombergGPT show the training route at much higher cost.

Why small local models instead of GPT-4?

Financial documents are often confidential, so running locally matters. Local models cost nothing per call, so we could make 7,805 calls. Two sizes from the same family (Qwen3 1.7B and 8B) let us isolate the effect of model size. The code also supports API models with --model openai:gpt-4o-mini and others.

Why Qwen3?

Open weights, strong maths for its size, available in several sizes of the same family, runs in Ollama on a laptop (Q4_K_M quantization), and has a switchable thinking mode, which gave us an extra ablation.

What is your contribution? What is new?

(1) VPSC, a training-free grounding check inside program self-consistency, with an exact ablation. (2) A new Indian annual-report calculation set (44 questions, ₹ crore/lakh), verified against the PDFs. (3) A controlled head-to-head of 7 hand-written strategies vs DSPy and TextGrad on small local models, with one-time optimization cost, confidence intervals and paired tests. (4) Diagnostics: error taxonomy, perturbation test, ablations. (5) An app where every answer can be audited.

Prompting strategies

What is the difference between zero-shot and few-shot CoT?

Zero-shot just adds “think step by step”. Few-shot first shows 3 solved examples as previous chat turns, so the model copies the format and approach. Our examples are FinQA train questions, so they never overlap the test.

Why did zero-shot CoT beat few-shot CoT on the 8B model (75 vs 70)?

The difference is not significant (McNemar p = 0.42). Possible reasons: the examples more than double the prompt (≈2,750 vs 1,280 tokens) and the 8B model already knows the reasoning format, so examples add little and may bias it toward the example formulas.

Why is Direct so bad?

The model has to output the final number immediately, with no space to write intermediate numbers. Each token is one forward pass, so it cannot do multi-step arithmetic “in its head”. Reasoning text acts as a scratchpad. The 8B model does better (37%) because it can do some simple calculations directly.

What is the repair step in Program-of-Thought?

If the code fails (syntax error, missing ans, a blocked import), we send the error message back once and ask for corrected code. Only 1–2% of questions needed it (average calls 1.01–1.02).

How does the majority vote work exactly?

Answers are rounded to 2 decimals as vote keys, so 16.4028 and 16.40 count as the same. The most common key wins; on a tie, the answer seen first wins, which is the greedy sample (sample 0). Agreement = winning votes / 5.

Why one greedy and four sampled paths?

Sample 0 at temperature 0 equals the single-call strategy, so self-consistency can only add information on top of it. The other four at T = 0.7 give diversity. Fixed seeds keep it reproducible.

VPSC (expect several questions here)

Explain VPSC in one breath.

Sample five Python programs, run each in the sandbox, throw away any program that types a number not found in the report, and take a majority vote over the rest; if none is grounded, vote over all of them. The idea: most errors are evidence errors, so check the evidence.

VPSC did not beat PoT-SC. So what is the point?

Correct, accuracy is identical on all three datasets, and we report that honestly. The reason is that the 1.7B model’s five programs nearly always agree, and when it uses a number that is not in the report it does so in all five, so filtering cannot change the vote. But every question the check flagged (6/6) was answered wrongly, so it is a precise reliability signal: in a real system you would show a warning or abstain. The method is also free: it reuses the same five programs.

Is 6 out of 6 enough to claim anything?

It is a small number, so we claim precision, not a general rate: when the flag fired it was right every time in our data. Coverage is low (6 of 44 wrong FinQA answers). A larger test set is in future work.

Why does the check catch so few wrong answers?

It only catches numbers that do not appear anywhere in the report (misreads, made-up values). Most evidence errors use a number that is in the report but from the wrong row or year. Catching those needs a cell-level check that the number comes from the right row and column, which is our proposed next step.

Why are 100, 1000, 10⁷ allowed in the code?

They are percentage and unit-conversion constants (thousand, lakh = 10⁵, million, crore = 10⁷, billion) and small counts like 2 for an average or 9 years for a CAGR, plus years 1900–2100. A number from the report may also be rescaled by 100, 0.01, 1000 or 0.001 (e.g. $1.1 billion written as 1100 million).

How is VPSC different from VeriFin or other verifiers?

VeriFin checks numbers against structured XBRL data with a Z3 logic solver; that needs XBRL-tagged US filings. VPSC needs no structured data, no solver and no training: it checks against the plain table text, so it works on Indian PDFs.

Why is PoT-SC a fair ablation?

It uses the same prompt, temperatures and seeds, so it gets exactly the same five programs (even the same cache entries). The only difference is the grounding filter, so any difference is caused by verification alone.

Prompt optimization

How does DSPy BootstrapFewShot work?

It runs our Chain-of-Thought program on FinQA training questions and keeps up to 3 runs that our scorer marks correct as demonstrations. The demos are the model’s own reasoning. It then uses those demos in the prompt for new questions.

How does TextGrad work?

Like gradient descent, but the “gradient” is text. The system prompt is the parameter. For each wrong answer in a mini-batch, the 8B model writes feedback on what went wrong and what instruction would prevent it. The optimizer combines that feedback and rewrites the prompt. We keep a rewrite only if accuracy on 40 dev questions does not drop; otherwise we revert.

Why did the optimizers do worse than hand-written prompts?

Three reasons. (1) Small validation set: 40 questions, also used to choose which rewrites to keep, so TextGrad’s 62.5% dev accuracy is optimistic and did not transfer to test. (2) The optimized TextGrad prompt became long and added a “say the calculation cannot be performed” rule, so the small model sometimes gave no number (10% format failures vs 2%). (3) DSPy’s demos are the 1.7B model’s own reasoning, which is weaker than our hand-written examples, and DSPy’s field-based prompt format is less natural for a small model. The lesson: for small models, careful hand-written prompts are competitive, and optimization has a real one-time cost (318 minutes for TextGrad).

Could the optimizers have seen the test set?

No. They use only 50 FinQA train and 40 FinQA dev questions. The test samples come from separate test files, and DSPy’s cache is turned off so the cost is real.

Where is MIPROv2?

It is implemented in dspy_opt.compile_program with auto="light", Bayesian search over instruction and demo candidates. Its run did not finish within our compute time, so there is no artifact and no result; the app and slides mark it as pending. We do not report any number for it.

Data

Why only 100 questions per dataset?

Compute. Every strategy × model × dataset combination is a separate run, and multi-sample strategies make 5 calls per question; everything ran on one laptop (about 30 hours total). We use the same fixed sample everywhere, report 95% confidence intervals (about ±10 points) and use paired tests that are valid at this size. --n 0 runs the full test sets.

How do you know the Indian gold answers are right?

Gold answers are never typed: each question has a formula that is executed in the sandbox. The build script checks every formula number is in the table, and that every transcribed cell appears in the text of the cited PDF page. A separate re-check confirmed all 44 operands are on the cited pages and all 44 answers recompute exactly. A test re-runs every formula.

Why include the Indian set?

FinQA and TAT-QA are US/international reports in dollars. Indian reports use ₹ crore and lakh, Indian digit grouping (1,25,000) and brackets for negatives. It tests whether the methods generalize, and existing Indian benchmarks cover regulatory text or look-ups, not multi-step calculations over annual-report tables.

Why only arithmetic questions from TAT-QA?

Our topic is numerical reasoning. TAT-QA also has span and counting questions that test extraction, not calculation, and need a different scorer.

What is “evidence” in FinQA (table_3, text_5)?

FinQA annotates which table rows and sentences are needed. We use the same ids for our retrieval units, which lets us measure recall@k directly.

Evaluation and statistics

Isn’t a 0.5% tolerance too lenient?

It is close to FinQA’s own execution accuracy, which accepts rounding differences. We also report accuracy at 1% tolerance and strict 2-decimal exact match for every run, so a reader can apply a stricter rule. The ranking of strategies stays the same.

Why accept both 12.5 and 0.125?

FinQA stores 12.5% as 0.125 while TAT-QA stores 12.5, and our prompt asks for percent numbers. Without this, correct answers would be marked wrong only because of the dataset’s convention. We only do it when the question is about a percentage, ratio, margin, growth and similar.

What is a bootstrap confidence interval?

We resample the 100 right/wrong results with replacement 2,000 times, compute accuracy each time, and take the middle 95% of those accuracies. It needs no assumption about the distribution. With 100 questions it is about ±10 points.

Why McNemar and not a t-test or comparing CIs?

All strategies answer the same questions, so the data is paired. McNemar uses only the questions where the two strategies disagree and is exact via the binomial distribution. Comparing two independent CIs ignores the pairing and is too conservative; a t-test assumes continuous data.

What does Holm correction do?

When you run many tests, some small p-values appear by chance. Holm sorts the p-values and multiplies the smallest by the number of tests, the next by one less, and so on, keeping them increasing. It controls the probability of even one false positive, and is less conservative than plain Bonferroni.

Your CIs overlap. Can you claim anything?

Yes, for big differences: Direct vs reasoning is significant everywhere, and thinking mode vs not is significant (p = 0.020). For differences among reasoning strategies we explicitly say they are not significant. That is itself a useful finding: the choice among reasoning prompts matters less than having reasoning at all.

Why are exact match and accuracy so different for CoT?

Text reasoning rounds intermediate values (e.g. writes 0.219 then multiplies), so the final answer is close but not equal at 2 decimals. PoT computes in full precision, so its EM is almost its accuracy (56 vs 57 on FinQA).

How is the error taxonomy decided? Is it reliable?

Rule-based, checked in a fixed order: no answer, execution error, sign, scale, near miss, no work shown, evidence error (a gold operand is missing from the model’s work), reasoning error (all operands present, wrong formula). It is reproducible and fast, but heuristic: for example a number that appears by coincidence can hide an evidence error. Human annotation of a sample is in future work.

Engineering

Is the sandbox really safe?

Four layers: an AST check before running (only math can be imported, no dunder attributes, no open/exec/eval/getattr/os/sys), a separate isolated Python process, a whitelist of builtins, and a 5-second timeout plus CPU limit. It is designed for arithmetic code. It is not a full security container: it does not set a memory limit, and a production system should add one (or run in a container). Tests check that imports, file access, dunder tricks and infinite loops are blocked.

Isn’t the response cache cheating?

No. A cache hit is returned only for an identical request (same model, prompt, temperature, seed and settings), which would give the same answer anyway. It stores the original token counts and latency, so costs are not understated. It lets long runs resume after a crash and makes re-analysis free. A new question is always answered live.

How do you count tokens and cost?

Ollama returns prompt_eval_count and eval_count for every call. We add them per question, and report tokens per question and tokens per correct answer. Local models cost $0; for API models cost_usd uses per-million-token prices.

How are runs reproducible?

Fixed sample seed (42), temperature 0 for single calls, fixed seeds per sample (42 + sample id), pinned library versions in requirements.txt, every answer saved as a JSON line, and analysis that re-scores saved answers. Re-running a finished experiment replays the cache.

How does the PDF upload work?

pdf_utils.page_to_example opens the page with pdfplumber, tries its detected tables, and also builds a table from lines that end in numbers (statement pages are often not real PDF tables). It keeps whichever has more usable rows; the rest of the lines become text. The column names come from the page’s year heading (for example “31st March 2025 31st March 2024” → columns 2025 and 2024, or “31.03.2024 31.03.2023”), and each row’s last numbers are placed under those years, with note references in a Note column.

Be honest about its limits: turning a PDF into a table is a hard problem. On single statement pages (Titan p275, Asian Paints p12, Marico p253) it works; on pages with two statements side by side it can mix rows. Across all 44 Indian questions answered from raw PDF pages, Program-of-Thought gets 18/44, versus 34/44 from our verified tables. That is why the experiments use transcribed, verified tables; better table extraction is future work.

Why Streamlit?

It turns Python into a web app without writing HTML or JavaScript, so the app calls the exact same library functions as the experiments. That guarantees the demo shows the real pipeline.

Results and interpretation

What does the bigger model change?

On FinQA every strategy gains 16–32 points (e.g. few-shot CoT 52 → 70, PoT 57 → 73). The biggest gain is for Direct (+32), and evidence errors drop sharply, so size mostly helps with reading the right number. Prompting still matters: 8B Direct (37%) is far below 1.7B PoT (57%).

Why does retrieval make accuracy worse?

Recall@5 is 78% on FinQA: about one in five gold rows is not in the top 5, and then the question cannot be answered. One report page fits easily in the model’s context, so giving the full page is better. Retrieval becomes necessary for whole 300-page reports, which is future work.

Why is thinking mode better but not your default?

It is the one significant improvement (49% → 63%, p = 0.020), but it costs 2× tokens and 13× the time (151 s vs 11 s per question). We kept it off for the main grid so every strategy is compared on equal terms and the grid fits our compute budget; it is reported as an ablation.

Which strategy would you recommend in practice?

For a small local model: Program-of-Thought with few-shot examples. It is the best or near-best single call, costs one call, gives exact arithmetic, and its code is auditable. Add the grounding check as a free warning flag. Use thinking mode if latency does not matter.

Why are Indian results higher than FinQA?

Our Indian tables are clean transcriptions and the questions state the period and unit clearly, while FinQA has noisy extracted text and some ambiguous questions. So it is a sign of generalization across currency and formatting, not proof that Indian reports are easier in general.

Limitations and future work

What are the main limitations?
  • Small samples (100/100/44) give ±10-point intervals.
  • One model family (Qwen3), and the 8B grid is incomplete.
  • Grounding is value-level: it checks a number exists, not that it comes from the right cell.
  • Error labels are rule-based.
  • Single pages, not whole reports.
  • MIPROv2 did not finish.
What would you do next?

Run the full test sets and the remaining 8B experiments; add larger and API models; make the check cell-level (row and column must match the question) and let the system abstain when flagged; human-annotate errors; extend retrieval to full reports; finish MIPROv2.

If you had to name one lesson?

For numerical questions, make the model show its work, preferably as code, and spend effort on getting the right numbers from the document; voting and automatic optimization add cost but little accuracy for small models.
